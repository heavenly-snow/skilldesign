# 项目知识清点

一个项目交付之后，把它涉及的知识提取出来，逐条判断你掌握了没有，只教缺的那部分。

**它不是 code review。** 不评价代码好坏、不找 bug、不算技术债。项目只是知识的落点。

用在任何能读文件、能对话的 AI 上（Claude Code、Codex、Cursor、Hermes、或直接把本文粘进对话框）。

## 什么时候用

- 「清点一下」「这个项目做完了，看看涉及哪些知识」「哪些我没掌握」
- 想巩固一个刚交付的项目，而不是审查它
- 连续做同类项目，想识别出反复出现的短板

**不要用于：** 代码质量审查、性能调优、安全审计、纯知识问答。

## 前置条件

- AI 能读项目文件（或你能把关键文件贴给它）
- 一个存放账本的位置（默认项目根目录的 `knowledge-ledger.md`，也可以放在个人笔记里）

有没有 git 不影响使用。有 git 是加分项（提交记录里有高质量的返工信号），没有就从产物结构反推。

## 四步

```
① 提取   项目涉及哪些知识  →  技术轨 + 业务轨
② 判断   你逐条说 会 / 不会 / 不用会
③ 教学   只讲「不会」的，一批一条因果链
④ 记账   进账本，下次已会的自动跳过
```

第②步必须由**你本人**判断，不要 AI 打分、不要出考试题。只有你知道自己当时是不是在瞎蒙。

---

## 第 0 步 · 读项目

按信息密度排序：

1. **提交记录**（如果有）——`git log --oneline`。找返工信号：`fix` / `harden` / `raise X to Y` / `merge A into B` / `refactor`。这类提交背后是真实踩过的坑，必须在清单里点到。
2. **目录树 + 行数**——搞清楚复杂度分布在哪几个文件
3. **核心模块源码**——按依赖顺序读（存储 → 业务 → 入口），不要按文件名字母序
4. **文档与配置**——README、部署文件、配置项

**完成标准**：能说出这个项目的三个主要复杂度来源，以及哪些文件承载了它们。

---

## 第 1 步 · 提取技术轨

### 三条硬规则

**① 组织轴是知识域，不是代码模块。**
按文件或模块遍历一遍再输出，得到的必然是审计报告。先列域，再把落点填进去。

**② 每条写成问句，不写断言。**

```
❌ 这里用 timeout=60 硬扛，没开 WAL，有隐患
✅ 写锁是库级还是表级？两种 journal 模式下读写会不会互相阻塞？超时耗尽抛什么？
```

断言只能让人防御，问句才能让人回答「会 / 不会」。问题要卡在三类地方：

- **边界**：它和相邻概念的分界线在哪
- **机制**：走一遍会发生什么，状态怎么变，哪一步会卡住
- **失效**：什么时候会坏，用错会怎样

**③ 落点精确到函数。**

```
app/db.py › claim_next_pending()
app/ui/main.py › render_batch_list()
docker-compose.yml › services
```

从项目根开始写相对路径，函数带 `()` 便于直接搜索。找不到函数就退到模块级，不许只写「在数据库那层」。

### 知识域骨架

按项目裁剪，不必全用。**按复杂度占比排序，最重的域放最前面**。

| 域 | 覆盖什么 |
|---|---|
| 并发与锁 | 锁粒度、事务边界、隔离级别、竞态 |
| 任务队列 | 认领、重试、幂等、毒丸、租约 |
| 并发执行模型 | 线程/进程/GIL、IO 密集 vs CPU 密集 |
| 远程调用 | 超时、重试、流式、协议细节 |
| 不可信输入 | 解压炸弹、路径穿越、限额分层 |
| 文件与产物 | 命名空间、静默覆盖、原子写 |
| 状态与一致性 | 状态机、派生状态、跨资源补偿 |
| 进程生命周期 | 崩溃恢复、stale 状态、部署假设 |
| UI 执行模型 | 重跑语义、状态存放、轮询成本 |
| 时间 | naive/aware、时区、过期计算 |
| 部署运行时 | 容器、卷、编排、配置外置 |

前端、数据管道、机器学习项目各有一套自己的域，照这个思路重新划。

### 粒度判据

一个条目合格的唯一标准：**它能被讲清三要素——是什么 / 怎么运转 / 能干什么。**

两种不合格：

- **太粗**：`Python`、`并发`、`数据库` —— 讲不出「怎么运转」，因为它是领域不是模型
- **太细**：`某个库的某个参数`、`某个 API 的用法` —— 是速查表，不是知识

正确的中间层：`事件循环与协程调度`、`缓存一致性策略`、`限流算法的取舍`、`租约与 fencing token`。

自检：给每条默写一句「它在内部是怎么跑起来的」。写不出 → 粒度不对。

### 输出形态

```
**A1 · 知识点的名字**
问：……？……？……？
落点：`相对路径 › 函数()`

**A2 · ……**
```

编号按域分组（A/B/C 各一个域），最后给一句：**嫌多就只判 A/B/C 这 N 条，其余扫一眼标「不用会」。**

没有这个降级选项，使用者看到二十条会直接放弃。

## 第 1 步 · 提取业务轨（两半，别混）

### (a) 领域知识 —— 可迁移

这个**行业本身**的知识，换一个同类项目照样用。判断标准：它属于业务，不属于这个实现。

例：音频格式与码率、文件大小↔时长↔耗时的关系、某类算法的固有难度、领域的典型失败模式。

从代码里通常只能看到一部分。**看不到的标「需要你补充」，不许编业务场景。**

### (b) 设计决策 —— 必须打 △

△ 的含义：**只看到结果，看不到决策过程。** 如果那是当时顺手写的、不是权衡过的，它就不是知识，只是这次的事实。

判断法一句话：**换个做法会怎样？** 另一个选择也说得通 → 别当知识。

### 反事后归因

从结果反推理由，任何结果都能找到听起来对的理由。最常见的一种是把限制包装成洞见：

> ❌「供应商能力边界决定了产品分期」 ← 实际只是「这家厂商的接口不支持某个字段，当时妥协了」

规则：

- 只写**有明确替代方案、且选择付了代价**的决策，格式是「选择 X / 替代 Y / 代价 Z」，不写「X 是正确做法」
- 拿不准是设计还是顺手写成 → 打 △，交给使用者判定
- 永远不要把「这次的妥协」说成「产品的路标」

---

## 第 2 步 · 判断

把清单交给使用者，让他按三条判：

- **会** — 三问全过
- **不会** — 任一条卡住
- **不用会** — 属于配方

### 三问（"掌握"的可操作定义）

缺了这个知识，会不会剥夺你的指挥权？

1. **验收**：AI 在这块给你错了，你能发现吗？
2. **纠偏**：发现了，你能说清哪里错、该怎么改吗？
3. **预防**：提需求时，你知道这里有个坑要提前交代吗？

任一条答「不能」→ 不会。

### 配方 vs 模型

判据**不是**「AI 能不能一秒生成」，是**缺了它会不会剥夺指挥权**。

| | 例子 | 结论 |
|---|---|---|
| 配方 | 镜像源配置、CSS、文档里查得到的参数、一次就会的语法 | 不用会，学它 ROI 为负 |
| 模型 | 运行时语义、并发模型、协议、状态机、一致性 | 必修 |

**要主动预判配方并单独列一张表**，否则使用者的判断力会被二十条噪音耗尽。

### 给固定回复格式

```
会：A1 A2 B1
不会：B2 B3
不用会：其余
```

否则他要一次打十几条，会放弃。

## 第 3 步 · 教学

### 先诊断，再决定讲什么

看他的答题模式。最常见的是：

- 「为什么需要它」答得出 → **目的层完整**
- 「它怎么运转」答不出 → **机制层空白**

这决定教学重心：**篇幅全给机制，不复述用途。**

把诊断结论直接告诉他。这一句话本身就有价值——它解释了「为什么我总觉得懂了但一动手就废」。

### 一批 = 一条因果链

分批的依据不是「同类」，是**依赖关系**。选能被上一环逼出下一环的序列：

```
锁是库级的
  → 所以不能靠锁排队，只能靠条件更新
  → 条件更新要求「读和写在一条语句里」
  → 所以先查后改就有 TOCTOU
  → 认领完会失败，失败要重试
  → 重试产生新问题：过期的执行者还在跑
  → 用租约挡它
  → 租约的校验也必须是一条语句（回到上上环）
```

这样讲完，他拿到的不是一个知识点，是一个**可复用的结构**。

每批 3–5 条。超过 5 条，最后一条必然水过鸭背。

### 每条讲四件事

1. **机制**（占一半以上篇幅）：内部怎么运转，走一遍给他看
2. **绑定他自己的代码**：指到他的文件函数，不给通用示例
3. **准确的失效形态**：异常名、日志原文、错在哪一步
4. **和前面哪条同构**：知识成体系的标志是能互相引用

准确的异常名、准确的数字、准确的顺序——这三点是「机制」和「概述」的分界线。

### 不许做

| 不许 | 为什么 |
|---|---|
| 讲成文档摘要 | 「它是一个轻量级数据库」这种句子零信息 |
| 复述用途 | 目的层他已经会了 |
| 一次超过 5 条 | 记不住 |
| 给通用示例 | 「假设一个订单系统」——他有真代码 |
| 编业务场景 | 看不到就说需要补充 |
| 结尾加「总之……」 | 总结不产生理解 |

### 验收

讲完一批，让他挑一条**用自己的话讲一遍**：

- 它是什么
- 它怎么运转
- 什么时候会咬人

不要问「懂了吗」。看他卡在哪一环：

| 卡点 | 说明 | 修法 |
|---|---|---|
| 卡在「怎么运转」 | 机制没进去 | 换个入口或比喻重讲 |
| 能讲运转但说不出失效 | 深度不够 | 补边界 |
| 讲得比原文还清楚 | 过了 | 记账 |

**通过标准**：能讲出「怎么运转」+「什么时候会坏」两句。只讲得出定义的不算。

## 第 4 步 · 账本

不是每个项目一份报告，是**一个持续累积的账本**。

每条记：知识点、所属域、状态、复现次数、首次出现、落点、卡点。

状态四档：

| 状态 | 含义 |
|---|---|
| 不会 | 待学 |
| 已学 | 讲过，未在真实项目里验证 |
| 已掌握 | 在下个项目里实际用出来过 |
| 不用会 | 配方，或 △ 判定为只是这次的取舍 |

**复现次数**是排序依据：同一知识点在不同项目出现就 +1。

- 1 次：可能只是这次业务的偶然
- 2 次：这个阶段的关键缺口，提级
- ≥3 次：系统性短板，优先于一切单点

下次清点先读账本：已掌握的跳过，不会的再次出现就提级，连续两次「不用会」的静音。

模板见 `../templates/ledger.md`。

## 反模式自查

| 症状 | 修正 |
|---|---|
| 输出读起来像 code review | 换轴：从代码模块换成知识域；删掉所有「隐患 / 建议」 |
| 条目是陈述句，不知道怎么答 | 全部改成问句，问边界和失效 |
| 落点只写到模块 | 补到 `文件 › 函数()` |
| 一次讲太多 | 按因果链切批，每批 ≤5 |
| 只讲「是什么」 | 机制占一半以上篇幅 |
| 业务轨把现有设计全说成对的 | 打 △，用「换个做法会怎样」筛一遍 |
| 问题比知识多 | 每条必须能讲三要素，讲不出就调颗粒度 |
| 编造业务场景 | 标「需要你补充」 |

## 验收清单

- [ ] 清单按知识域分组，最重的域在最前
- [ ] 每条是问句，不是断言
- [ ] 每条落点到文件 + 函数
- [ ] 配方类已预判并单独列出
- [ ] 业务轨的设计决策都打了 △
- [ ] 教学按因果链分批，每批 ≤5 条
- [ ] 每条都讲了机制，不只是用途
- [ ] 使用者能复述「怎么运转」
- [ ] 账本已更新
