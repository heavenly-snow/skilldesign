# 提取细则

## 一、先列域，再填落点

不要边读代码边往外蹦条目——那样输出顺序会跟着文件顺序走，读起来就是 code review。

先按项目的复杂度占比排出 8–12 个域，最重的放最前面，然后把落点填进去。

### 通用域骨架（后端 / 服务类）

| 域 | 覆盖什么 |
|---|---|
| 并发与锁 | 锁粒度、事务边界、隔离级别、竞态 |
| 任务队列 | 认领、重试、幂等、毒丸、租约 |
| 并发执行模型 | 线程/进程/GIL、IO 密集 vs CPU 密集 |
| 远程调用 | 超时、重试、流式、协议细节 |
| 不可信输入 | 解压炸弹、路径穿越、限额分层 |
| 文件与产物 | 命名空间、静默覆盖、原子写 |
| 状态与一致性 | 状态机、派生状态、跨资源补偿 |
| 进程生命周期 | 崩溃恢复、stale 状态、部署假设 |
| 时间 | naive/aware、时区、过期计算 |
| 部署运行时 | 容器、卷、编排、配置外置 |

### 换项目类型时重新划

**前端 / 客户端**

渲染与重绘时机、状态管理的单向性、异步竞态（取消与过期响应）、缓存失效、路由与生命周期、可访问性、打包产物与按需加载。

**数据处理 / 管道**

分区与并行度、倾斜与热点、幂等与可重跑、背压、schema 演化、迟到数据的窗口语义、Exactly-once 到底保证了什么。

**机器学习 / 推理服务**

训练与服务的一致性（特征对齐）、批处理与延迟的权衡、显存与批大小的非线性、指标与真实目标的对齐、数据泄漏、模型版本与回滚。

### 领域知识（业务侧）

行业本身的常识，换一个同类项目照样用。从代码通常只能推断出一部分，缺的标「需要你补充」。

例：音频格式与码率、文件大小↔时长↔耗时的关系、某类算法的固有难度、该行业的典型失败模式。

## 二、粒度判据

合格标准只有一条：**能被讲清三要素——是什么 / 怎么运转 / 能干什么。**

| 错误 | 例子 | 为什么 |
|---|---|---|
| 太粗 | `Python`、`并发`、`数据库` | 讲不出「怎么运转」，它是领域不是模型 |
| 太细 | 某个库的某个参数、某个 API 的用法 | 是速查表，不是知识，AI 一秒给你 |
| 合格 | `事件循环与协程调度`、`缓存一致性策略`、`租约与 fencing token` | 能讲三要素，且缺了会咬人 |

**自检**：给每条默写一句「它在内部是怎么跑起来的」。写不出 → 粒度不对，往中间调一层。

## 三、表述模板

```
**A1 · 知识模型名**
问：<2–3 个追问>
落点：`相对路径 › 函数()`
```

### 三类问法

问题要卡在假懂的人答不出的地方：

**边界型**：「它和相邻概念的分界线在哪」
> 事件循环 vs 线程池 vs 多进程，同一个 IO 密集任务，什么时候必须用哪个？

**机制型**：「走一遍会发生什么 / 状态怎么变 / 哪一步会卡住」
> 一个 await 让出控制权之后，其它协程是怎么被调度回来的？

**失效型**：「什么时候会坏 / 用错会怎样」
> 把 CPU 密集逻辑放进协程里会怎样？表现是什么？

失效型最能暴露假懂，因为要说出「用错」就得真知道失效模式。

### 反面

- ❌ `这里用 timeout=60 硬扛，没开 WAL，有隐患`（断言 + 评价）
- ✅ `写锁是库级还是表级？两种 journal 模式下读写会不会互相阻塞？`（可回答）

## 四、落点格式

```
app/db.py › claim_next_pending()
app/ui/main.py › render_batch_list()
docker-compose.yml › services
src/hooks/useAuth.ts › useAuth()
```

- 从项目根开始，用相对路径，不用绝对路径
- 函数 / 方法带 `()`，便于直接搜索
- 跨文件的知识点写多个落点，用 `/` 分隔
- 纯配置、无函数可指时退到键名或服务名
- 找不到具体函数才退到模块级，**不许只写「在数据库那层」**

## 五、业务轨：两半，不许混

### (a) 领域知识 —— 可迁移

属于行业，不属于这个实现。换一个同类项目照样用。

### (b) 设计决策 —— 必须打 △

只看得到结果，看不到决策过程。**如果那是当时顺手写的、不是权衡过的，它就不是知识，只是这次的事实。**

判断法：**换个做法会怎样？** 另一个选择也说得通 → 别当知识。

### 反事后归因

从结果反推理由，任何结果都能找到听起来对的理由。最常见的是把限制包装成洞见。

规则：

- 只写**有明确替代方案、且选择付了代价**的决策，格式「选择 X / 替代 Y / 代价 Z」
- 拿不准 → 打 △，交回使用者
- 永远不要把「这次的妥协」说成「产品的路标」

## 六、配方清单

独立列一张表，标「建议不用会」，让使用者一眼扫过。

配方 = AI 一秒能给、缺了不影响指挥权：镜像源、CSS、文档里查得到的参数、一次就会的语法。

**预判配方是必须做的**，否则使用者的判断力会被二十条噪音耗尽。

## 七、常见错误

| 症状 | 根因 | 修法 |
|---|---|---|
| 清单像 code review | 按模块读代码 | 先列域，再填落点 |
| 条目太碎 | 把 API 当知识 | 往上提一层到模型 |
| 条目太虚 | 把领域当知识 | 往下落到具体机制 |
| 业务轨像在辩护 | 从结果反推理由 | 标 △ + 「换个做法会怎样」 |
| 漏掉最重的 | 按文件顺序读 | 按复杂度占比排域，主干先出 |
| 使用者看不下去 | 一次给二十条 | 给降级选项：只判主干 |
